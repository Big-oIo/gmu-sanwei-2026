## 零、先看懂几个词（术语速查表）

这些词全篇会反复出现，先花 3 分钟扫一遍，后面就不懵了：

| 术语 | 大白话解释 |
|------|-----------|
| **STEP / .stp** | 一种通用的三维模型文件格式，用"面、边"描述一个零件。我们库里 10 万个零件都是这种文件 |
| **B-Rep** | "边界表示"，即用面、边、顶点来描述实体，是 CAD 的工业标准 |
| **嵌入（embedding）** | 把一个零件转成一串数字（叫"向量"）。越像的零件，这串数字越接近 |
| **向量** | 就是一串数字，比如 (0.2, 0.8, -0.1, …) 有几百上千个数 |
| **FAISS** | Facebook 出的一个工具，专门"快速找出最接近的向量"，用来做检索 |
| **索引（index）** | 把一大堆向量预先组织好，方便快速查找的结构。可以存盘、下次直接加载 |
| **license / 授权** | 商业软件的"许可证密钥"。HOOPS 是收费软件，没密钥就运行不了 |
| **conda** | 一个管理"Python 运行环境"的软件，能装多个互不干扰的环境 |
| **pip** | Python 装包的命令 |
| **WSL** | "Windows 里的 Linux 子系统"，让你在 Windows 电脑上跑 Linux |
| **Docker** | "容器"，把软件打包成开箱即用的环境，避免安装冲突 |
| **GPU** | 显卡，做大量计算比 CPU 快很多倍，训练/大批量处理通常需要 |
| **Recall@k** | 检索指标：前 k 个结果里，"命中了相关零件"的比例 |
| **mAP** | 平均精度，衡量检索排序质量的一个综合指标 |
| **自检索 / 自检** | 让系统检索"它自己"，用来确认管线没接错（自己找自己必然能中） |

## 角色①　项目负责人 / 方案架构

### 1. 职责范围、交付物、协作边界

**你是"项目经理 + 方向决策者"。不一定要写代码，但要保证大家不跑偏、有进度、能对外交代。**

- **职责范围**：写总体技术方案、把任务分给②③④、定汇报口径、组织周会、最后汇总对外汇报。
- **交付物**：①《总体技术方案》文档；②任务分工表；③周会纪要；④阶段性汇报材料（PPT/文档）。
- **协作边界**：
  - 你**不负责**具体装环境、跑数据、做评测（那些是②③④的活）；
  - 你**负责**：谁卡住了、需要谁配合、方向对不对、怎么跟团队讲；
  - 你是**对外汇报的唯一出口**，其他人不直接对外汇报（避免口径不一致）。

### 2. 需要掌握的知识与技能（程度要求）

| 知识/技能 | 需要掌握到什么程度 |
|-----------|-------------------|
| 看懂项目流程 | 能说清"零件→向量→索引→检索"这四步就够了 |
| Word / PPT / 在线文档 | 会写文档、做简单表格 |
| 沟通协调 | 会组织线上/线下短会、会催进度 |
| 术语 | 看懂上面的术语表即可，不用会写代码 |

### 3. 执行方法与步骤（手把手）

**第一步：读材料，搞懂背景**
- 做什么：把《三维计划报告(1).docx》、BRepNet 那两份报告（PPT+Word）通读一遍。
- 怎么做：重点搞清三件事——项目要干嘛、现在到哪一步、卡在哪。
- 做完的标准：你能用大白话给队友讲清楚"我们从哪来、要到哪去"。

**第二步：写《总体技术方案》（对应 A3，可立即开工，不依赖环境）**
- 做什么：写一份 2~4 页的方案文档。
- 怎么做：至少包含三块内容——
  1. **主线模型**：用 HOOPS 的"整模型向量"（一个零件一个向量，1024 维压到 512 维）；
  2. **三段产物形态**：①零件嵌入向量 → ②FAISS 索引文件 → ③检索脚本/服务（写清楚最终交付的就是这三样）；
  3. **模块划分与依赖顺序**：照抄文末的依赖图即可。
- 做完的标准：②③④ 任何一个人拿到方案，都知道自己要交付什么。

**第三步：建任务分工表**
- 做什么：把 A1~A11 分到②③④。
- 怎么做：用飞书/腾讯文档建一张表，列四栏：任务、负责人、截止时间、状态。
- 做完的标准：每个 A 任务都有人认领，没有人重复认领。

**第四步：定汇报口径（尤其一条红线）**
- 做什么：跟全组统一"什么能对外说、什么不能说"。
- 怎么做：重点强调这条红线——
  > "自检索 100% 是数学必然（自己跟自己比距离为 0），只能叫'管线自检'，**不能当检索准确率汇报**。"
- 做完的标准：每个组员都能复述这条红线。

**第五步：组织周会（全程）**
- 做什么：每周开一次短会（15~30 分钟）。
- 怎么做：每次固定问三句话——谁卡在哪了？需要谁配合？下周交付什么？
- 做完的标准：会后产出一份 5 行以内的纪要。

**第六步：汇总汇报（A11）**
- 做什么：把②③④的成果拼成对外汇报的材料。
- 怎么做：按"背景→进度→结果→下一步"结构整理，突出数据和卡点。
- 做完的标准：读者能看懂、能据此推进下一步。

### 4. 需要提前了解或注意的事项

- **别自己闷头写代码**：你的价值在方向和协调，技术活交给别人。
- **红线反复强调**：谁在汇报里把"自检索 100%"说成准确率，谁就犯大错。
- **三段产物形态必须写清**：否则后面的人不知道最终要交付什么。
- **时间安排**：A3 方案建议第 1 周内出草稿；A11 汇报在里程碑节点做。

## 角色②　环境与算力工程师

### 1. 职责范围、交付物、协作边界

**你是"开路先锋"，负责打通全项目唯一的硬阻塞——环境。这是 4 个角色里技术要求最高的。**

- **职责范围**：选运行环境、装 HOOPS AI 及依赖、配 license 授权、处置"三个坑"、测 Windows 可行性、定算力方案。
- **交付物**：①一套能用的运行环境；②《环境搭建手册》（别人能照做复现）；③授权验证记录；④Windows 可行性结论；⑤三个坑的处置结论。
- **协作边界**：
  - 你**负责**：环境能不能跑通，跑通了别人才有活干；
  - 你**不负责**：具体检索、评测（那些是③④）；
  - 你是③的**前置**，③的 A4/A5/A7 都得等你环境通了才能做。

### 2. 需要掌握的知识与技能（程度要求）

| 知识/技能 | 需要掌握到什么程度 |
|-----------|-------------------|
| Linux 基本命令 | 会用 `cd`（进目录）、`ls`（看文件）、装包命令即可 |
| conda / pip 装包 | 会照着教程敲命令、看报错 |
| 看报错日志 | 报错时能看懂"错在哪一行、缺了什么" |
| Docker（可选） | 会用基础命令即可，不用精通 |

> 建议由有编程基础、或愿意边学边做的同学担任。如果实在没人会，这个角色可以"边查边做"，但要多留时间。

### 3. 执行方法与步骤（手把手）

**第一步：查官方文档**
- 做什么：打开 HOOPS AI 官网 `https://docs.techsoft3d.com/hoops/ai/`。
- 怎么做：重点看"安装（Install）"和"评估（Evaluate）"两节，官方 readme 的安装流程是 Linux 的。
- 做完的标准：你能说出"装 HOOPS AI 一共要装哪几样东西"。

**第二步：选运行环境（关键决策）**
- 做什么：决定在哪台机器、用什么方式跑。
- 怎么做（按推荐顺序）：
  1. **首选 WSL**（Windows 里的 Linux 子系统）——最贴合官方 Linux 流程，免费；
  2. 或 **Docker 容器**——最省事，但要会一点 Docker；
  3. **不要裸装在 Windows 上**——大概率失败（除非后面实测证明可以）。
- 做完的标准：定下一个明确方案并写下来。

**第三步：装基础依赖**
- 做什么：装运行所需的底层库。
- 怎么做：Linux 下按 readme 提示装 `libglu1-mesa`、`xvfb`；再用 conda 建一个环境，用 pip 装 `hoops_ai`、`torch`、`dgl`、`pytorch_lightning`、`faiss`。
- 做完的标准：所有依赖装完，没有报错。

**第四步：配 license 授权并验证**
- 做什么：把密钥配进去，让软件能正常启动。
- 怎么做：license key 之前记录在项目里的 `hoops_readme.md` 文件中，找到它并配置；然后写一段最小测试代码验证。
- 做完的标准：运行 `import hoops_ai` 不报错。

**第五步：处置"三个坑"（计划里已列明）**
- 做什么：解决三个已知问题。
- 怎么做：
  1. **缺 `cad_tasks.py` 脚本** → 从官方教程仓库补全该文件；
  2. **格式只认 SolidWorks（.sldprt/.sldasm）** → 确认能否直接读 .stp，不能就找转换方案；
  3. **本机依赖全缺** → 逐个安装并记录版本号。
- 做完的标准：三个坑都写明了"怎么处置、结果如何"。

**第六步：跑最小测试**
- 做什么：验证环境真的能用。
- 怎么做：写一段测试，目标有两个——①`import hoops_ai` 不报错；②能成功读取 1 个 .stp 文件。
- 做完的标准：两件事都成功，截图留证。

**第七步：写《环境搭建手册》**
- 做什么：把前六步整理成文档。
- 怎么做：每一步写清"命令是什么、当时环境是什么、遇到什么错、怎么解决的"。
- 做完的标准：另一个同学照着手册能独立复现出同样环境。

### 4. 需要提前了解或注意的事项

- **conda 源连不上**：BRepNet 当初就栽在这。提前配清华/阿里镜像源，别用默认国外源。
- **license 有效期和授权范围**：需确认清楚（计划待解决问题 5），避免白装。
- **每步截图/记录**：否则别人复现不了，等于白装。
- **卡住要尽早暴露**：这个角色允许卡，但别拖到影响③开工。
- **时间安排**：A1 是全项目起点，建议第 1~2 周重点攻，越早通越主动。

## 角色③　数据与检索工程

### 1. 职责范围、交付物、协作边界

**你是"主力"，负责把 10 万个零件变成"可搜索的库"。技术要求中等，照着官方示例改参数即可。**

- **职责范围**：核定 10 万数据资产、建小批量子集、小批量端到端试跑、全量入库 + 索引存盘。
- **交付物**：①数据资产清单；②小批量试验子集；③索引文件（可复用资产）；④全量检索库；⑤全量入库耗时记录。
- **协作边界**：
  - 你**依赖②**：A4/A5/A7 都要等②的环境通了才能做（但 A2 数据核定可以提前做）；
  - 你**为④提供输入**：你跑出的小批量结果交给④做自检，全量库交给④做评测。

### 2. 需要掌握的知识与技能（程度要求）

| 知识/技能 | 需要掌握到什么程度 |
|-----------|-------------------|
| 跑 Python 脚本 | 会照着教程改几个参数、按回车运行 |
| 理解"嵌入→索引→检索"三步 | 能说清每步输入什么、输出什么 |
| FAISS 存盘/加载 | 会用 `save_shape_index` 存、`load_shape_index` 读 |
| 文件管理 | 会看目录结构、统计文件数量/大小 |

### 3. 执行方法与步骤（手把手）

**第一步：A2 数据核定（可与②并行，先做）**
- 做什么：摸清 10 万个 .stp 到底是什么。
- 怎么做：
  1. 数清楚有多少个文件、总大小（约 9.53 GB）、目录怎么组织的；
  2. 确认这批数据是不是 fabwave 数据集、使用/授权范围（计划待解决问题 4）。
- 做完的标准：产出一份数据清单（数量、格式、大小、来源、授权）。

**第二步：等②环境就绪（A1 完成）**
- 做什么：确认②已经把环境跑通。
- 怎么做：跟②确认"最小测试已通过、能读 .stp"。
- 做完的标准：你拿到了②给的《环境搭建手册》或口头确认。

**第三步：A4 建小批量试验子集**
- 做什么：从 10 万里抽一小批做试验。
- 怎么做：抽几十~几百个有代表性的 .stp，单独放一个文件夹。
- 做完的标准：子集已建好，数量明确，能代表整体。

**第四步：A5 小批量端到端试跑**
- 做什么：照着官方示例跑通完整流程。
- 怎么做：打开官方示例 `5b_cad_search_using_HOOPS_embeddings.ipynb`，跑通三步——
  1. **嵌入**：把子集里的零件转成向量；
  2. **建索引**：用 FAISS 建索引；
  3. **检索**：上传一个零件，看能否搜出相似的。
  - 重点：用 `save_shape_index` 把索引**存盘**，再 `load_shape_index` 加载验证能用。
- 做完的标准：索引能存盘、能加载、检索能返回结果。

**第五步：交给④做自检（A6）**
- 做什么：把 A5 的产物交接给④。
- 怎么做：告知④"索引在哪、怎么加载、小批量结果在哪"。
- 做完的标准：④能顺利接手。

**第六步：A7 全量入库**
- 做什么：小批量跑通后，把 10 万零件全部处理。
- 怎么做：批量嵌入 → 建索引 → 存盘，并**记录总耗时**（计划待解决问题 8）。
- 做完的标准：全量索引存盘成功，耗时记录在案。

### 4. 需要提前了解或注意的事项

- **全量 10 万嵌入会很慢**：A7 前先跟②确认算力（有没有 GPU、要不要多机）。
- **格式对口**：官方教程声明 .stp/.step，咱们正好是 .stp，一般不用转换。
- **索引一定要存盘复用**：跑一次就丢等于白干，save 下来才是资产。
- **先小批量再全量**：别一上来就 10 万，先小批量验证链路，避免白跑几小时。
- **时间安排**：A2 第 1 周可做；A5 在环境通后 1 周内；A7 视算力，可能数天。

## 角色④　评测与质量

### 1. 职责范围、交付物、协作边界

**你是"裁判"，负责定"什么算相似、检索对不对"的标准，并对结果把关。**

- **职责范围**：管线自检、定义"相似"并标注评测集、排除自身的真实评测、可选稳健性/对照实验。
- **交付物**：①评测集（查询 + 相关/不相关标注）；②评测指标报告（Recall@k / mAP）；③质量结论与问题分类。
- **协作边界**：
  - 你**依赖③**：A6 依赖③的 A5，A9 依赖③的 A7；
  - 你**依赖团队**：A8 里"相似"的定义必须跟团队对齐；
  - 你**为①提供结论**：①拿你的评测结果去对外汇报。

### 2. 需要掌握的知识与技能（程度要求）

| 知识/技能 | 需要掌握到什么程度 |
|-----------|-------------------|
| 检索评测指标 | 能解释 Recall@k（前 k 名命中比例）、mAP（排序质量）的含义 |
| 写/跑评测脚本 | 会照着模板改、运行 |
| 标注能力 | 能按规则给"相关/不相关"打标，并留档 |

### 3. 执行方法与步骤（手把手）

**第一步：A6 管线自检（依赖③的 A5）**
- 做什么：确认链路没接错。
- 怎么做：拿小批量结果做自检索，看命中是否 100%、自身分是否 0。
- 做完的标准：自检索命中 100%、自身分 0（**注意这只是自检，不是准确率**）。

**第二步：A8 定义"相似" + 标注评测集（可与③的 A7 并行）**
- 做什么：定"相似"的判定标准，并标一小批评测集。
- 怎么做：
  1. 先明确"相似"按什么口径（形状？局部特征？零件类别？）——计划待解决问题 2；
  2. 标一小批评测集：给出查询零件 + 哪些算"相关"、哪些算"不相关"。
- 做完的标准：评测集标注完成、口径明确、可复核。

**第三步：A9 排除自身的真实评测（依赖③的 A7 + 自己的 A8）**
- 做什么：真正检验检索能力。
- 怎么做：排除查询自身后，跑真实检索，计算 Recall@k、mAP 等指标。
- 做完的标准：产出一份带指标数字的评测报告。

**第四步：A10 稳健性/对照（可选）**
- 做什么：视②的 A1 结论，决定是否做扰动测试或 BRepNet 对照。
- 怎么做：如果做，按计划 PPT 第 9 页 P1/P2 所列内容扩展验证。
- 做完的标准：有结论即可，无强制。
