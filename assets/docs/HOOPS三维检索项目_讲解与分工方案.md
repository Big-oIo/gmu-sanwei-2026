> 基于《三维计划报告(1).docx》整理　|　整理日期：2026-11-08
> 技术路线：HOOPS（已采用主线）　|　历史方案：BRepNet（已归档）

## 第一部分：背景与概念讲解

### 1. HOOPS 是什么

HOOPS 是美国 **Tech Soft 3D** 公司的商业 3D 软件工具包（很多工业 CAD 软件的显示内核、数据交换内核都来自它）。2026 年 3 月它发布了 **HOOPS AI**，专门给 CAD 零件做机器学习。

对本项目最有价值的是它提供的一条**成品检索流水线**：

```
读零件(.stp) → 编码成 1 个向量 → 存入 FAISS 索引 → 上传新零件 → 检索出最相似的
```

关键特点：
- **一个零件 = 一个向量**（1024 维压到 512 维），不是每个面一个向量；
- **预训练用 100 万模型**（对比学习，303 万参数），有现成整模型权重，不用自己训练；
- **自带 FAISS 索引**（一种快速向量搜索技术），索引可存盘、下次直接加载复用。

**类比**：BRepNet 相当于"自己买零件攒一台检索机器"；HOOPS 相当于"买一台成品检索机器，插电就能用"。

### 2. HOOPS 的技术成熟度

- 是**商业产品**：有官方文档、6 个教程、成品检索示例、预训练权重，比学术开源项目规范。
- 但**很新**：1.0 版 2026 年 3 月才发布；官方文档主要是 Linux 流程，**Windows 原生能否运行未验证**。
- 需要**商业授权（license）**：有有效期与使用范围限制（是计划中的一个待解决问题）。
- 结论：**工具本身是成品、成熟度在产品层面高；但"咱们本机把它跑起来"这件事尚未验证**。

### 3. HOOPS 在项目中处于什么程度

**处于"零起点"。**

- ✅ 已有：4 个预训练权重、官方 5b 端到端检索示例、10 万个 .stp 零件文件，均已核对。
- ❌ 没有：HOOPS 软件一个都没安装，conda 环境也没有，真实零件一次都没跑过。
- 卡点：环境（Linux + HOOPS AI + 授权）未打通 —— 即计划中的 A1，是"唯一硬阻塞"。

一句话：**东西都备齐了，但机器还没通电。**

### 4. BRepNet 是什么（计划中的"BREPT"）

BRepNet 是 **Autodesk（欧特克）** 的学术开源项目（CVPR 2021）。它本来的任务是"给零件每个面分 8 类"（**面分割**），**不是整模型检索器**。我们之前是"借用"它给每个面算出的向量（中间结果），再自己写脚本做检索。

### 5. BRepNet 当初为何被放弃

三个原因叠加（文档已写明）：

1. **旧依赖装不上**：需要 Python 3.7 / PyTorch 1.7.1 / OCC 等老版本，2026-09-02 装环境时 conda 软件源连接失败，一直没装成。
2. **真实零件一次都没跑过**：之前只验证了 6 个合成假模型，真实 STEP 零件从未推理，无法证明真实检索能力。
3. **检索要自己从头写**：BRepNet 没有现成检索功能，我们自写约 290 行脚本、仅依赖 numpy，且没有索引存盘（每次重算）。

而 HOOPS 正好补上这三点：成品链路 + 100 万模型权重 + 官方 FAISS 索引 + 格式对口 10 万 .stp。

**注意：BRepNet 不是"作废"，而是"归档"。** 它的实验包、9 页 PPT、9 章报告保留下来，作为汇报模板与历史验证成果。

## 第二部分：需求分析

### 需求清单（需求编号 / 描述 / 优先级 / 验收标准 / 对应任务）

| 编号 | 需求描述 | 优先级 | 验收标准 | 对应任务 |
|------|---------|--------|---------|---------|
| R1 | 打通 Linux + HOOPS AI 运行环境与授权 | P0 | 目标环境能 `import hoops_ai` 不报错；license 验证通过；记录 Windows 原生可行性实测结论 | A1 |
| R2 | 核定 10 万 STEP 数据资产与来源/授权 | P0 | 产出文件清单（数量、格式、大小、目录）；确认是否 fabwave 数据集及使用范围 | A2 |
| R3 | 产出总体技术方案与任务分解 | P0 | 确定主线模型、三段产物形态（嵌入/索引/检索服务）、模块划分与依赖图 | A3 |
| R4 | 建立小批量试验子集 | P0 | 从 10 万里抽出有代表性的小批 .stp（几十~几百个）作为端到端验证集 | A4 |
| R5 | 小批量端到端试跑 | P0 | 小批完成 嵌入→FAISS 索引→检索；索引成功存盘并可 reload；拿到第一批真实产物 | A5 |
| R6 | 管线自检（自检索） | P1 | 自检索命中率 100%、自身分 0（仅证明链路接对，非准确率） | A6 |
| R7 | 全量入库：10 万零件批量嵌入 + 索引存盘 | P1 | 10 万批量嵌入完成、索引存盘、记录总耗时、索引可复用 | A7 |
| R8 | 定义"相似"并标注一小批评测集 | P1 | 明确相似判定口径；产出"查询+相关/不相关"标注集 | A8 |
| R9 | 排除自身的真实相似检索评测 | P1 | 排除查询自身后，输出 Recall@k / mAP 等检索指标 | A9 |
| R10 | 稳健性 / 对照实验（可选） | P2 | 扰动/重导出稳健性测试，或 BRepNet 对照；是否启动由 A1 结论定 | A10 |
| R11 | 整理阶段性汇报材料 | P2 | 对外交付可汇报的 PPT/文档 | A11 |

> 说明：R6 自身检索 100% 是数学必然（自己跟自己比距离为 0），只能当"管线自检"，不能当检索准确率汇报 —— 这是必须守住的汇报红线。

## 第三部分：4 人分工方案

### 角色与职责总览

| 角色 | 定位 | 核心职责 | 负责模块 |
|------|------|---------|---------|
| ① 项目负责人 / 方案架构 | 总协调 + 对外汇报的唯一出口 | 总体技术方案、主线模型与三段产物形态、模块划分与依赖、汇报口径、跨角色协调、里程碑把控 | A3、A11、全局进度 |
| ② 环境与算力工程师 | 打通硬阻塞的"开路先锋" | Linux/WSL/Docker 环境、HOOPS AI 安装、license 授权核验、三个坑处置、Windows 可行性实测、算力方案 | A1 |
| ③ 数据与检索工程 | 把 10 万零件变成检索库的"主力" | 数据资产核定、小批量子集、小批量试跑、全量入库 + 索引存盘 | A2、A4、A5、A7 |
| ④ 评测与质量 | 定"对错"标准、把关质量的"裁判" | 管线自检、定义相似 + 标注评测集、排除自身真实评测、稳健性对照、质量关卡与汇报红线 | A6、A8、A9、A10 |

### 协作关系与依赖顺序

关键路径（串行）：`A1 → A4 → A5 → A6 → A7 → A9 → A11`

可并行推进：A2（数据核定）、A3（技术方案）可与 A1 并行；A8（评测集标注）可与 A7 并行。

- ②环境工程师的 **A1 是唯一起点**，是所有人的前置。
- ③数据工程师的 A2 可与 A1 并行；A4/A5/A7 依赖 ② 的 A1。
- ①负责人的 A3 不依赖环境，可立即启动。
- ④评测的 A6 依赖 ③ 的 A5；A9 依赖 ③ 的 A7 + ④ 的 A8；A10 是否启动由 ② 的 A1 结论决定。
- ①负责人的 A11 汇总所有人成果，作为最终交付。
