# HOOPS 三维检索项目 · 4 人分工操作手册

> 面向完全不懂技术的新同学　|　整理日期：2026-11-08
> 目标：把《三维计划报告》拆成 4 个人能直接照做的任务清单

阅读方法：找到你被分配的角色那一节，从"任务清单"开始看，按"执行步骤"一条条做，
做完对照"产出成果"确认，遇到问题看"常见问题与注意事项"。

## 角色① 项目负责人 / 方案架构

### 一句话定位
你是"项目经理 + 方向决策者"，不一定要写代码，但要保证大家不跑偏、有进度、能对外交代。

### 任务清单
| 编号 | 任务 | 对应计划 |
|------|------|---------|
| 1-1 | 吃透项目背景与计划 | 通读 |
| 1-2 | 写《总体技术方案》 | A3 |
| 1-3 | 把 A1~A11 拆成每个人的待办 | A3 |
| 1-4 | 定"汇报口径"（含红线） | A11 前 |
| 1-5 | 组织每周同步、推动卡点 | 全程 |
| 1-6 | 汇总成果，写汇报材料 | A11 |

### 执行步骤（按顺序）
1. **通读三份材料**：《三维计划报告(1).docx》、之前 BRepNet 的 PPT 和 DOCX 报告，弄清楚"从哪来、到哪去"。
2. **写技术方案草稿**（与②③的 A1/A2 并行，不依赖环境）：
   - 主线模型：HOOPS 整模型向量（1024→512 维）；
   - 三段产物形态：①零件嵌入向量 → ②FAISS 索引文件 → ③检索服务/脚本；
   - 模块划分与依赖顺序（可参考下方依赖图）。
3. **建一张任务表**（推荐用在线表格或飞书/腾讯文档），把 A1~A11 分配到②③④，标清负责人、截止时间、状态。
4. **定汇报口径**，尤其是这条红线：
   > 自检索 100% 是数学必然（自己跟自己比距离为 0），只能叫"管线自检"，**不能当检索准确率汇报**。
5. **每周开一次短会**，问三句话：谁卡在哪了？需要谁配合？下周交付什么？
6. **每个里程碑汇总一次**，最后把所有人的成果拼成对外汇报的 PPT/文档（A11）。

### 产出成果
- 《总体技术方案》文档
- 任务分工表（含负责人/时间/状态）
- 周会纪要
- 阶段性汇报材料（PPT/文档）

### 需要掌握的技能/工具
- 不强制会写代码；
- 会用 Word/PPT 或在线协作文档；
- 能看懂项目大致流程（读文档即可）；
- 沟通协调、催进度。

### 常见问题与注意事项
- **别自己闷头写代码**：你的价值是方向和协调，技术活交给②③④。
- **红线要反复强调**：谁在汇报里把"自检索 100%"说成准确率，谁就犯大错。
- **三段产物形态一定要写清楚**，否则后面的人不知道最终要交付什么。

## 角色② 环境与算力工程师

### 一句话定位
你是"开路先锋"，负责打通全项目唯一的硬阻塞——环境。这是 4 个角色里**技术要求最高**的，建议由有编程基础、或愿意边学边做的同学担任。

### 任务清单
| 编号 | 任务 | 对应计划 |
|------|------|---------|
| 2-1 | 选运行环境（Linux/WSL/Docker/云） | A1 |
| 2-2 | 安装 HOOPS AI 及依赖 | A1 |
| 2-3 | 配置 license 授权并验证 | A1 |
| 2-4 | 处置"三个坑" | A1 |
| 2-5 | 实测 Windows 能否原生运行 | A1 |
| 2-6 | 定算力方案并留痕 | A1 |

### 执行步骤（按顺序）
1. **先调研官方文档**：打开 HOOPS AI 官网 `https://docs.techsoft3d.com/hoops/ai/`，重点看"安装"和"Evaluate"章节（readme 里的安装流程是 Linux 的）。
2. **选环境**（关键决策）：
   - 优先选 **WSL**（Windows 里的 Linux 子系统）或 **Docker 容器**，因为官方流程是 Linux 的；
   - **不要裸装在 Windows 上**，大概率失败（除非后面实测证明可以）。
3. **装基础依赖**：Linux 下按 readme 提示装 `libglu1-mesa`、`xvfb` 等；再准备 conda/pip 装 `hoops_ai`、`torch`、`dgl`、`pytorch_lightning`、`faiss`。
4. **配授权**：license key 之前已记录在 `hoops_readme.md` 里；配置后写一段最小测试代码验证。
5. **处置三个坑**（计划里已列明）：
   - 缺 `cad_tasks.py` 脚本文件 → 从教程仓库补全；
   - 格式只认 SolidWorks（.sldprt/.sldasm）→ 确认能否直接读 .stp，否则找转换方案；
   - 本机依赖全缺 → 逐个安装并记录版本。
6. **写最小测试**：目标是跑通 `import hoops_ai` 不报错 + 能成功读取 1 个 .stp 文件。
7. **把整个过程写成《环境搭建手册》**，让其他同学能照着复现。

### 产出成果
- 一套能用的运行环境
- 《环境搭建手册》（可复现）
- license 授权验证记录
- Windows 可行性实测结论
- 三个坑的处置结论

### 需要掌握的技能/工具
- Linux 基本命令（cd、ls、安装包）
- conda / pip 装包
- 会看报错日志
- （可选）Docker

### 常见问题与注意事项
- **conda 源连不上**：BRepNet 当初就栽在这。提前配清华/阿里镜像源。
- **license 有效期和授权范围**：需确认清楚（计划待解决问题 5）。
- **每一步截图/记录**：否则别人复现不了，等于白装。
- **装不动就求助**：这个角色允许卡住，但要尽早暴露，别拖到影响③的工作。

## 角色③ 数据与检索工程

### 一句话定位
你是"主力"，负责把 10 万个零件变成"可搜索的库"。技术要求中等，照着官方示例改参数即可。

### 任务清单
| 编号 | 任务 | 对应计划 |
|------|------|---------|
| 3-1 | 核定 10 万 STEP 数据资产 | A2 |
| 3-2 | 建小批量试验子集 | A4 |
| 3-3 | 小批量端到端试跑 | A5 |
| 3-4 | 全量入库 + 索引存盘 | A7 |

### 执行步骤（按顺序）
1. **A2 数据核定（可与②并行）**：
   - 数清楚 10 万 .stp 有多少个、多大（约 9.53 GB）、目录结构长什么样；
   - 确认这批数据是不是 fabwave 数据集、使用/授权范围（计划待解决问题 4）。
2. **等②的环境就绪**（A1 完成）后，开始 A4：
   - 从 10 万里抽几十~几百个有代表性的 .stp 作为试验子集。
3. **A5 小批量试跑**：照着官方 `5b_cad_search_using_HOOPS_embeddings.ipynb` 这个示例，跑通三步：
   - 嵌入：把零件变成向量；
   - 建索引：用 FAISS 建索引；
   - 检索：上传一个零件，看能不能搜出相似的。
   - 重点：用 `save_shape_index` 把索引**存盘**，再 `load_shape_index` 加载验证能用。
4. **把结果交给④做自检（A6）**。
5. **A7 全量入库**：小批量跑通后，把 10 万零件全部批量嵌入、建索引、存盘，并**记录总耗时**。

### 产出成果
- 10 万数据资产清单
- 小批量试验子集
- 索引文件（可复用资产）
- 全量检索库
- 全量入库耗时记录

### 需要掌握的技能/工具
- 能跑 Python 脚本、按教程改参数
- 理解"嵌入 → 索引 → 检索"三步
- 会用 FAISS 存盘/加载

### 常见问题与注意事项
- **全量 10 万嵌入会很慢**：A7 前先跟②确认算力方案（GPU 还是多机）。
- **格式对口**：官方教程声明 .stp/.step，咱们正好是 .stp，一般不用转换。
- **索引一定要存盘复用**：跑一次就丢等于白干，save 下来才是可复用资产。
- **小批量先跑通再全量**：别一上来就 10 万，先小批量验证链路。

## 角色④ 评测与质量

### 一句话定位
你是"裁判"，负责定"什么算相似、检索对不对"的标准，并对结果把关。

### 任务清单
| 编号 | 任务 | 对应计划 |
|------|------|---------|
| 4-1 | 管线自检（自检索） | A6 |
| 4-2 | 定义"相似"并标注评测集 | A8 |
| 4-3 | 排除自身的真实评测 | A9 |
| 4-4 | 稳健性/对照实验（可选） | A10 |

### 执行步骤（按顺序）
1. **A6 自检（依赖③的 A5）**：拿小批量结果做自检索，确认命中 100%、自身分 0——这**只证明链路接对**。
2. **A8 定义"相似"（可与③的 A7 并行）**：
   - 先和团队/同学确定"相似"按什么口径判定（形状？局部特征？零件类别？）——这是计划待解决问题 2；
   - 标一小批评测集：给出查询零件 + 哪些算"相关"、哪些算"不相关"。
3. **A9 真实评测（依赖③的 A7 + 自己的 A8）**：
   - 排除查询自身后，跑真实检索；
   - 计算检索指标：Recall@k（前 k 名里命中多少）、mAP 等。
4. **A10 稳健性/对照（可选）**：视②的 A1 结论决定是否做扰动测试或 BRepNet 对照。

### 产出成果
- 评测集（查询 + 相关/不相关标注）
- 评测指标报告（Recall@k / mAP）
- 质量结论与问题分类

### 需要掌握的技能/工具
- 懂检索评测指标（Recall、mAP、MRR 的含义）
- 会写/跑评测脚本
- 能跟团队对齐"相似"的定义

### 常见问题与注意事项
- **"相似"必须先问团队**：定义没对齐，评测全是白做。
- **守住红线**：自检索 100% 不是准确率，别在报告里混为一谈。
- **评测集要能复核**：谁标的、标了什么，都要留档，别拍脑袋。
